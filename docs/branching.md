# Гілки, коміти та pull request

Цей документ описує, як команда працює з гілками й комітами в репозиторії `team-devops-handbook`. Правила обов'язкові для всіх учасників, і більшість із них підтримано налаштуваннями репозиторію, тому порушити їх технічно складно.

## 1. Принципи

- `main` завжди в робочому стані й захищена правилами репозиторію.
- Прямі коміти в `main` заборонені: усі зміни проходять через pull request.
- Гілки короткоживучі: одна гілка відповідає одному завданню й видаляється після злиття.
- Кожен PR схвалює інший учасник команди.
- Історія `main` лінійна: один PR дорівнює одному коміту.

## 2. Іменування гілок

Формат: `тип/короткий-опис`, латиницею, малими літерами, слова через дефіс.

- `docs/` для документації: `docs/branching`
- `feat/` для нової функціональності: `feat/add-search`
- `fix/` для виправлення помилки: `fix/broken-link`
- `chore/` для службових змін (налаштування, хуки): `chore/repo-setup`

Назви на кшталт `test`, `new`, `patch-1` не використовуємо: з них не зрозуміло, про що гілка.

## 3. Робочий цикл

1. Оновіть `main` і створіть гілку:
   ````
   git switch main
   git pull --prune
   git switch -c docs/my-topic
   ````
2. Робіть невеликі логічні коміти:
   ````
   git add docs/my-topic.md
   git commit -m "docs: add my topic"
   ````
3. Відправте гілку на GitHub:
   ````
   git push -u origin docs/my-topic
   ````
4. Відкрийте pull request у `main`. Заголовок у форматі конвенції комітів (розділ 5), в описі: що зроблено, навіщо, як перевірити.
5. Пройдіть рецензію, виправте зауваження в тій самій гілці.
6. Після схвалення злийте через Squash and merge.
7. Прибирання після злиття:
   ````
   git switch main
   git pull --prune
   git branch -D docs/my-topic
   ````
   Після Squash and merge Git не вважає гілку злитою: у `main` з'являється один новий коміт, а коміти гілки не стають його предками, тому `git branch -d` зазвичай відмовляється видаляти гілку з повідомленням «not fully merged». Використовуйте `-D`, але лише переконавшись, що PR справді злито, бо `-D` видаляє без перевірки.

## 4. Оновлення гілки відносно main

Якщо `main` пішов уперед, оновлюйте свою гілку через rebase, а не через злиття `main` у гілку:

````
git fetch origin
git rebase origin/main
git push --force-with-lease
````

Так в історії немає зайвих комітів «Merge branch main into …». Rebase переписує коміти вашої гілки, тому після нього потрібен force push. `--force-with-lease` безпечніший за `--force`: він відмовиться пушити, якщо на сервері є чужі коміти, яких ви не бачили. Force push на власну гілку допустимий, а на `main` заблокований правилами.

Якщо rebase зупинився на конфлікті, виправте файл, виконайте `git add <файл>` і `git rebase --continue`. Скасувати rebase можна командою `git rebase --abort`. Приклад розбору конфлікту дивіться в `conflict.md`.

## 5. Конвенція комітів

Перший рядок повідомлення має такий формат:

````
тип(область): короткий опис у наказовому способі
````

Область необов'язкова. Довжина першого рядка до 72 символів — це рекомендація: локальний хук перевіряє лише формат, а не довжину.

Типи:

- `feat` нова функціональність
- `fix` виправлення помилки
- `docs` зміни в документації
- `style` форматування без зміни змісту
- `refactor` перебудова без зміни поведінки
- `test` тести
- `chore` службові зміни (налаштування, хуки)

Правильно: `docs(branching): add naming rules`, `fix: correct link to review guide`, `chore: add commit-msg hook`.

Неправильно: `update` (нічого не пояснює), `Fixed stuff` (немає типу), `docs: .` (немає опису).

Заголовок PR теж пишемо в цьому форматі, бо при Squash and merge саме він стає повідомленням коміту в `main`.

## 6. Pull request

- Один PR відповідає одній темі. Оптимальний розмір до кількох сотень рядків змін.
- Опис містить три частини: що зроблено, навіщо, як перевірити.
- Автор не зливає PR без схвалення: це заблоковано правилами репозиторію.
- Зауваження закриваємо через Resolve conversation лише після виправлення.

## 7. Локальний хук

Репозиторій містить хук `commit-msg`, який відхиляє повідомлення коміту не за форматом. Хуки не завантажуються разом із репозиторієм автоматично, тому після клонування виконайте один раз:

````
git config core.hooksPath .githooks
````

Хук локальний: його можна обійти через `git commit --no-verify`, і він не діє на коміти з веб-інтерфейсу GitHub. Тому форматування заголовків PR ми перевіряємо ще й на рецензії.

## 8. Заборонено

- Пушити в `main` напряму та force-пушити в `main`.
- Зливати PR merge-комітом (вимкнено в налаштуваннях).
- Комітити секрети, ключі, файли `.env`.
