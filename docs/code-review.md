# Рецензування pull request

Цей документ описує, як ми рецензуємо зміни в `team-devops-handbook`, і зберігає журнал реальних рецензій, які відбулися під час роботи над довідником.

## 1. Правила репозиторію

Прямі коміти в `main` заборонені, зміни йдуть лише через pull request. Для злиття потрібне одне схвалення від іншого учасника, а для файлів із CODEOWNERS ще й від власника файлу. Автор не може схвалити власний PR. Нове схвалення потрібне після кожного нового коміту, бо попередні скидаються. Незакриті розмови блокують злиття. Зливаємо лише через Squash and merge. Bypass list порожній: правила діють і на власника репозиторію, тож обійти їх не можна.

## 2. Як ми рецензуємо

1. Читаємо опис PR і розуміємо, що має вийти.
2. Відкриваємо Files changed і читаємо всі зміни. Для Markdown відкриваємо View file, щоб побачити відображений текст.
3. Команди з документів виконуємо самі, а не лише читаємо.
4. Коментуємо конкретні рядки через Start a review.
5. Завершуємо рішенням: Request changes, Approve або Comment.
6. Після виправлень перевіряємо лише нові зміни («Changes since your last review»).

### Позначки коментарів

Кожен коментар починається з позначки: `blocking:` означає проблему, без виправлення якої злиття заборонене; `suggestion:` пропозицію, рішення за автором; `question:` питання, відповідь на яке може змінити оцінку; `nit:` дрібницю, що ніколи не блокує; `praise:` відзначення вдалого рішення.

Коментар пишемо за схемою «що бачу, чому це проблема, що пропоную». Критикуємо текст чи код, а не людину.

## 3. Чек-лист

- Зрозуміло, що змінено й навіщо; немає сторонніх файлів.
- Посилання й шляхи до картинок відкриваються у відображеному вигляді.
- Команди виконано, вони працюють у тому вигляді, як написані.
- Документ не суперечить іншим файлам і реальним налаштуванням репозиторію.
- Немає секретів і особистих шляхів.
- Скрипти перевірено на «поганому» і «хорошому» вході, повідомлення про помилку каже, як виправити.

## 5. Типові знахідки

Найчастіше знаходили не помилки синтаксису, а розбіжності між текстом і реальністю: документ описує команду, яка не працює так, як сказано (`git branch -d`), файл, якого ще немає (`.gitattributes`), чи посилання, яке не відкривається. Їх видно лише тоді, коли рецензент виконує команди й відкриває відображений вигляд, а не просто читає текст.

Друга група знахідок стосується налаштувань, які працюють не так, як здається при читанні файлу: CODEOWNERS із одним власником блокує злиття, CRLF на Windows ламає скрипти.

Третя група стосується повноти: документ формально є, але ним неможливо скористатися, бо немає пояснень чи прикладів.
