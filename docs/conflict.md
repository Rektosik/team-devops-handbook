# Розбір конфлікту злиття

## Що сталося

Два учасники одночасно змінили один і той самий рядок у `README.md` у різних гілках, створених від одного стану `main`:

- `docs/readme-b` (PR #5, учасник B): «Командний довідник, що пояснює, як працювати з гілками, pull request і рецензуванням.»
- `docs/readme-a` (PR #6, учасник A): «Довідник командної роботи з Git: гілки, коміти, конфлікти та правила репозиторію.»
- Початковий рядок у `main`: «Спільний довідник, у якому описано процес командної роботи з Git.»

PR #5 злили першим. Після цього в PR #6 з'явився напис «This branch has conflicts that must be resolved». Git не вирішує такі випадки сам, бо не знає, який із двох нових варіантів рядка правильний.

![Конфлікт у PR](assets/conflict-pr.png)

## Як виглядає конфлікт

Гілку `docs/readme-a` я оновлював командою `git rebase origin/main`, і Git зупинився з конфліктом у `README.md`:

````
<<<<<<< HEAD
Командний довідник, що пояснює, як працювати з гілками, pull request і рецензуванням.
=======
Довідник командної роботи з Git: гілки, коміти, конфлікти та правила репозиторію.
>>>>>>> 3f2a1b4 (docs: rewrite handbook purpose)
````

Що означають маркери: блок між `<<<<<<< HEAD` і `=======` це моя гілка, а блок між `=======` і `>>>>>>>` приходить із `main`.

![Маркери конфлікту](assets/conflict-markers.png)

## Помилкове вирішення

На тимчасовій гілці я залишив лише власний рядок (в редакторі «Accept Incoming Change»), а блок B видалив, і завершив rebase. Git не видав жодної помилки, але команда `git diff origin/main -- README.md` показала, що рядок з PR #5 зник: замість нього стоїть мій.

![Помилкове рішення: чужу зміну втрачено](assets/conflict-wrong-diff.png)

Чому це погано:

- чужу вже схвалену й злиту роботу втрачено без обговорення;
- ніхто цього не помітить, бо Git вважає конфлікт розв'язаним, а файл виглядає цілим;
- іншою поширеною помилкою було б закомітити файл із маркерами `<<<<<<<`, і тоді README зіпсовано.

Цю гілку я видалив і ніколи не публікував.

## Правильне вирішення

1. Прочитав обидва варіанти й зрозумів намір кожного: B пояснює роботу з гілками, PR і рецензуванням, а A додає коміти, конфлікти й правила репозиторію.
2. Залишив один рядок, який поєднує теми обох, і видалив усі маркери:
   ````
   Командний довідник з Git: гілки, коміти, pull request, рецензування, конфлікти та правила репозиторію.
   ````
3. Позначив конфлікт розв'язаним і завершив rebase:
   ````
   git add README.md
   git rebase --continue
   ````
4. Оновив гілку на GitHub:
   ````
   git push --force-with-lease
   ````
   Force push потрібен, бо rebase переписав історію гілки. `--force-with-lease` перед записом перевіряє, що на сервері немає чужих комітів, яких я не бачив, тому нічиєї роботи не затре. Правила репозиторію блокують force push лише на `main`, на власній гілці він допустимий.

![Правильне рішення](assets/conflict-right.png)

## Rebase чи merge

Merge додає окремий коміт злиття, і в історії з'являється розгалуження. Rebase переносить мої коміти поверх оновленого `main`, і історія лишається прямою. Для нас важлива лінійна історія, тому гілки оновлюємо через rebase.
